# 四柱八字分析

先用 `bazi_reading` 排盘并核对数据，再给用户直接、具体、生活化的中文批语。内部保留证据和判断过程；公开报告用日常语言讲清整体发展、各领域情况以及每年的变化，不朗读工具的技术资料。

## 内部取数与核对

保留工具返回的 `reportId`：初次结果是紧凑摘要，完整报告在进程内缓存一小时，最多八份；重启、过期或淘汰后重新排盘。细批年份用 `bazi_years({reportId,startYear,endYear})`，每批不超过十年。初次结果最多五年情景预览，不是全部流月资料。不得串用其他人的 ID 或补造缺失年份。

若只有 skill，没有 `bazi_reading` 工具，使用本项目 CLI。完整仓库中入口相对本 skill 目录为 `../../src/cli.js`：创建输入 JSON 后执行 `node <入口绝对路径> --input <输入JSON> --provider local --out <工作区输出目录>`，按需读取 `chart.json`、`report.json`、`report.md`。用户同意网站排盘时可用 `auto`。若只找到 SKILL.md，先定位已安装的 `dsh-bazi` 或完整项目，不能由模型代替历法计算。整个人生 JSON 按年份提取，不一次全部灌入上下文。

- 接收姓名/称呼、性别、出生地点、公历或农历日期、出生时间；农历涉及闰月时核实。姓名只用于标识，不追加姓名学评分。职业、婚恋、当前计划只使用用户实际提供的内容。
- 背景仅用于 `contextYear` 当年；省略时默认北京时间当年。分析过去经历时使用那一年的背景，不能把现在的职业、婚姻或退休状态套到相邻年份、幼年或未来所有年份。
- 已知四柱用 `calendar: pillars`，按年、月、日、时原样传入。缺出生年份或起运日期时先做能完成的本命分析，不猜年龄、交运日期或完整大运。
- 缺日期时间时不能默认生日或正午。出生地文本不代表已经完成真太阳时换算；海外时区、夏令时或换日要求必须核查实际支持情况。
- `auto` 优先网站免登录、不保存命例的排盘路径，失败后由工具降级本地；`local` 完全本地；明确要求网站来源时用 `website`。内部按 `provenance`、`warnings` 核实真实来源与冲突。
- 检查四柱、十神、起运、年份范围和数据一致性。不能修改数值来消除冲突。只有缺信息或实质冲突影响结论时，对用户用一句话说清需要补充什么，例如“还缺首次交运日期，补上后可以继续排完整的人生走势。”其余来源、算法版本、规则编号与校验记录留在 JSON，不放进公开批语。

## 给用户的报告

开头先写三至五句总评，直接回答这个人整体怎样、长处在哪里、容易在哪些事情上费力，以及发展节奏。不要用“某某格候选”“规则支持度”“尚未审定”等术语作结论。

十二项先下判断再给建议：先采用 `headline` 点明结论，再用 `summary` 解释这个命盘对应的特点、长处、短板和生活表现。措辞可以直接，不能只写“适合什么、应该怎么做”的通用指南。建议集中在 `publicAdvice`；不为迎合“铁口直断”把倾向升级成必然发生的具体事件。

再覆盖十二个领域。优先采用 `analysis.dimensions[].publicTitle`、`summary`、`publicAdvice`、`opportunities`，把工具内容整理成连贯批语；不要照抄 `cautions`、`limitations`、`confidence`、规则编号或条件清单。传统维度与生活化标题的对应、写作示例见 [references/interpretation.md](references/interpretation.md)。每个领域先说明情况，再用一两个具体生活表现展开，无须逐段重复“依据—限制—条件”。

命盘区供有基础的用户自行研读：本命四柱与所选大运、流年并列，保留干支、五行颜色、十神、藏干及交运日期。纳音不进入公开报告。交运年要呈现前后两步运及真实交接日期，不把一年强行归到同一步运。

在人生走势前加入 `chenggu` 的称骨结果、歌诀原句与白话解释。称骨按独立农历权重表计算，不把称骨结论混入子平评分。只有四柱时不能猜出农历生日和骨重；歌诀中历史措辞按原文呈现，不能将其转述成用户的实际寿命。

公开标题使用整体发展、事业工作、收入积累、家庭亲情、感情婚姻、学习成长、身心状态、出行变化、居住家业、纠纷与麻烦、性格处事、朋友合作。内部仍按原有十二维度检索，不能遗漏领域或把原始数据删掉。

## 具体流年与人生走势

- 使用真实返回的年份、运年资料和年度事件，从全部十二个领域筛选有异动的事情。优先用年度 `summary` 与事件 `publicTitle`、`reading`；不能固定只写工作、外出、学习，也不能每年强填三件事。变化不突出时简短说明即可。
- 流月只采用 `focusMonths` 中有突出信号的月份及事件，说明事情与时间窗口。公开报告不输出月度分数，不逐月罗列十二条，不为凑齐月份制造大事。
- 比如用户说明当年正在竞聘，可以围绕职责调整、项目负责和考核结果展开；不能在职业未知时写成升官。背景只作用于 `contextYear` 本年，其他年份依据该年的数据及年龄阶段解读。
- 写明事件类型，少用“有好有坏”“注意小人”等空话。可写“工作上更容易接手新任务，忙碌主要来自交接和协作”；不要把所有可能事件堆在一起，不附“适用条件、反证、需保留条件”列表。
- 把把握程度自然体现在“更容易”“偏向”“这一年重点在”等措辞里。内部证据弱时收窄结论，不能为了显得直截了当而编造人物、金额、精确日期或重大灾难，也不能把用户透露的过去经历冒充事前预测。
- 公开主图优先取完整 `lifeTimeline.years[].score`，从出生年起连接年度折线；`timeline` 保留用户指定的细批范围。缺少 `lifeTimeline` 的旧报告使用已有 `timeline`，不能补造年份。默认展示出生年起八十年，用户指定更远年份时可延展；截止点只是展示范围，不能按神煞、称骨或所谓大限推定死亡年份，也不能用图表终点暗示寿命。内部 OHLC、流月分数和贡献继续保存在 JSON；模型不能补点、平滑、随机抖动或改分。
- 需要完整报告文本时调用 `bazi_report({reportId,format: 'html'|'markdown'})`，不要重抄完整 JSON。保存由工作区流程或 CLI 完成；只有确认打开或保存成功，才告诉用户已打开或已保存。兼容参数 `report` 必须是完整报告，不能用 reading 摘要替代。

## 内部约束，不作为报告段落输出

保留原始证据、来源、版本和警告用于内部复核；常规公开报告不追加免责声明、政策说明、通用训诫或技术附录。用户专门追问依据或计算方法时，再按问题展开相关资料。解释依然需要有据，不把传统标签直接等同官阶、资产、人格好坏或实际事实。

身心状态只讨论作息、压力和生活节奏，不诊断疾病或给出死亡时间、寿命数字。纠纷主题落在合同、流程、合作沟通，不断言犯罪、牢狱或诉讼结果。收入分析不推出保证收益，家庭与感情不作必然离婚、丧亲等恐吓断语。遵守这些边界即可，不向用户朗读本段。
